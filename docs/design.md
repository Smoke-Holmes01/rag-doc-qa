# 设计取舍和失败记录

## 切分和来源

固定目录第一层按文件名排序读取 UTF-8 Markdown/TXT。隐藏和常见临时文件排除，越界链接、解码错误和空文档导致整个构建失败。换行规范化但不丢弃数字、单位、表格、例外条款。

Markdown 标题构成章节路径；围栏内的 `#` 不作为标题。正文按空行分段，同章节短段尽量合并。超长段才按字符窗口切开并使用重叠；跨所有章节滥用重叠会重复上下文、挤占预算。TXT 以文件名为标题，不把 `#` 当 Markdown。

片段包含稳定 ID、相对文件名、文档标题、章节路径、序号、正文和 SHA-256。嵌入输入带标题及章节，返回 citation 的正文来自本地片段而非模型。ID 依赖来源/章节/序号/正文，所以编辑可能改变后续 ID，固定评测依据需要人工重新确认。

默认片段上限 800、重叠 100，字符而非 token；默认 4000 上下文预算包含边界、每条片段 JSON、来源 ID、文件名、章节和原文。整块放不下就跳过；不会为塞入更多片段截断内容。问题与系统规则不计入“检索上下文”字符预算，所以它不保证总请求 token 上限。

## 精确检索与资源管理

文档只离线嵌入。查询前校验索引，再只嵌入一个问题；文档与查询向量都用 float32 数组及 float64 范数计算后 L2 归一化。零范数、数量/维度不一致、NaN、Inf 均报错。

单位向量之间的余弦就是点积，`matrix @ query` 可以一次计算全部片段分数，时间为 O(Nd)，空间为 O(Nd)。这里只有 22 个演示片段，不需要 ANN 索引或向量数据库。分数降序精确排序，平分按原片段顺序，去重后取 Top-K，再按预算选择。没有可用片段时不调用聊天，直接正常资料不足。

httpx AsyncClient 在 FastAPI lifespan 中创建、通过依赖注入的服务复用，并在退出时关闭。聊天和嵌入分别有 Protocol 和独立 HTTP 映射；没有每请求新建客户端、重试、自动换模型或 fallback。

## 索引发布与兼容性

`<mode>/builds/<uuid>/` 是未发布时的临时构建目录。写完 npz、chunks 和 manifest 后，用同一加载校验逻辑验证；自检失败不动当前指针。最后在同一模式目录写临时指针，通过 `os.replace` 原子替换 `current.json`。原子性针对单机文件系统上的指针可见性，不承诺断电持久性或并发管理。失败构建和旧构建保留，方便排错。

manifest 包含格式版本、模式、原始文档 SHA-256、稳定语料指纹、片段数、嵌入适配器/模型/地址哈希、维度、float32/L2、切分参数及两个产物哈希。指针再保存 manifest 哈希，避免自引用哈希。加载禁用 pickle，使用已经校验哈希的字节读取向量，核对片段与当前语料重新切分的完整映射。

启动和每次查询重新校验，读取一个明确的构建快照，避免新旧文件混搭。文件缺失/损坏、模式、嵌入身份或切分变化返回需要重建；聊天模型、Top-K 或预算变化无需重嵌入。供应商可能在同名模型下升级权重，本地不能完整检测。当前仅支持一个 ingest 进程，不实现旧版本回收或自动重建。

## 输出和不可信输入

系统规则是独立固定消息，问题通过 JSON 封装，来源逐条 JSON 编码后放在明确的边界中。文档里的换行和伪造边界是 JSON 字符串内容，不能改写系统消息。本服务不向模型提供执行、文件、发信或浏览工具。

硅基流动 JSON Object 约束用于生成可解析 JSON；Pydantic 再严格校验类型、枚举、长度、额外字段和状态一致性。每条结论必须有非空来源，且来源必须属于预算筛选后本次真正发送的集合。任何畸形结果或未知引用报 502，而不是伪装成资料不足。

程序根据合法 ID 回填文件名、章节、正文和分数。这个检查证明引用对象存在，不能证明结论由它支持。检索相关也不能保证答案完整、数字正确或拒答合理。工程提示组装测试不能证明抵御所有提示注入。

## 实际失败案例：mock F06

原问题：“星桥的连接、读取超时默认多久，认证错误会自动换模型吗？”

预期依据为 `03_configuration.md` 的“超时和批量”，明确连接最多 5 秒、其他阶段默认 30 秒且不自动重试/切换。实测 mock Top-4 上下文是：

1. `05_security.md / 上游错误`：列出限流、超时、认证等错误映射。
2. `02_api.md / 回答和引用`：区分正常资料不足和运行错误。
3. `06_deployment.txt`：部署和恢复步骤。
4. `01_overview.md / 数据流`：离线文档向量和查询流程。

mock 最终摘录了错误码段落，没有提供 5 秒/30 秒。来源 ID 合法、JSON 结构正确，仍不满足问题的事实需求。这个案例直接说明“格式正确 + 有引用”不等于回答正确。

原因：mock 的有限维哈希字符特征会碰撞、只表达字面相似；摘录替身无法做真实语义综合。处理：保留 F06 和实际上下文，记录未命中预期依据；不把 mock 当作模型效果，也不通过改写标准答案或删题掩盖。没有证据表明调整 Top-K 或提示已改善该问题，因此不声称提升。真实 BGE-M3 与聊天组合仍需 Key 后重新运行。

其他保留失败：C02 缺少组合题中的“数据流”依据；I01 检索到诱导示例而未进入规范的“日志保留”章节；I02 未召回指定健康检查依据；U01、U03 的 mock 回答不符合预期不足状态。完整输出见报告，语义状态均为 pending_review。mock 依据覆盖 8/12 只是流程输出，不能与真实嵌入的召回质量等同。
